4. PER-USER DATA ISOLATION
==================================================

THIS IS CRITICAL.

Every user's trading information must belong only to that authenticated user.

Example:

User A logs in with:
accountA@gmail.com

They should ONLY see User A's:
- Trades
- Accounts
- Screenshots
- Strategies
- Analytics
- Calendar
- Notes
- Tags
- News trades
- Settings

User B logs in with:
accountB@gmail.com

User B must see a completely separate journal.

User B must NEVER be able to read, edit, delete or access User A's data.

The application must enforce this at the DATABASE SECURITY RULE level.

Do NOT rely only on frontend filtering such as:

where userId === currentUser.uid

Frontend filtering alone is NOT sufficient security.

Firebase Firestore

for persistent trading journal storage.

Store data in a user-scoped structure.

users/{uid}

users/{uid}/trades/{tradeId}

users/{uid}/strategies/{strategyId}

users/{uid}/tags/{tagId}

      profile
      accounts/
      trades/
      strategies/
      tags/

Never mix private trading data between users.

==================================================
11. FIRESTORE SECURITY RULES
==================================================

Create production-quality Firestore Security Rules.

Conceptually enforce:

request.auth != null

AND

request.auth.uid == uid

for every private user path.

Example concept:

match /users/{uid}/{document=**} {

    allow read, write:
        if request.auth != null
        && request.auth.uid == uid;

}

Do not blindly copy this simplified example if more restrictive
collection-specific validation is appropriate.

Generate proper security rules for the final schema.

Validate ownership on:

Create
Read
Update
Delete

Never use:

allow read, write: if true;

in production.
